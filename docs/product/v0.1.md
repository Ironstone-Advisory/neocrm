# NeoCRM v0.1 product definition

## Product thesis

NeoCRM is not a list of leads with notes attached. It is a shared relationship record: a person or organization, their changing relationships, the conversations and commitments around them, and the commercial work they enable.

The core question it should answer is: **what is the complete, current context for this relationship, and what should happen next?**

## Intended users

- **Relationship owners** need a reliable account/contact view and a clear follow-up queue.
- **Commercial leads** need opportunities, offerings, and agreements connected to the people and organizations involved.
- **Operations** needs one canonical dataset rather than separate spreadsheets and point tools.
- **Leadership** needs an eventual view of relationship health and pipeline without asking each person for a manual update.

## v0.1 user journeys

1. Create or find a person or organization in a workspace.
2. Link a person to an organization, client, partner, advisor, or other party with a dated relationship.
3. Record a note, call, email, meeting, or event against every relevant party and, when relevant, an opportunity or agreement.
4. Create and complete a follow-up task from that context.
5. Create an offering and opportunity, associate its participants, and track it from discovery through outcome.
6. Convert or associate the opportunity with an agreement/engagement and retain its relationship timeline.

## Scope

### In

- workspace membership and tenant-scoped records;
- people, organizations, and typed many-to-many party relationships;
- activity timeline, including calendar-style events;
- task queue with due dates, owners, and contextual links;
- offerings (products/services), opportunities, and agreements;
- search-ready identifiers, timestamps, and external references;
- an API-first implementation with a web client to follow.

### Not in

- inbox, calendar, or contact-sync connectors;
- bulk email, marketing campaigns, lead scoring, and sequences;
- AI-generated updates or autonomous actions;
- custom objects, workflow automation, and report builder;
- external customer portal, mobile client, and multi-currency conversion;
- financial accounting, document signing, or contract-redlining.

Those exclusions keep v0.1 narrow enough to establish a trustworthy canonical model. They are extension candidates, not rejections.

## Experience principles

1. **Relationship-first:** every person and organization has context beyond a single pipeline record.
2. **Timeline-first:** facts and interactions are easy to append and hard to lose.
3. **One record, many contexts:** one party can participate in many opportunities, agreements, and activities.
4. **Explicit over inferred:** source, owner, role, and relationship labels are visible; automation comes after data trust.
5. **Human work stays visible:** activities describe what happened; tasks describe what must happen next.
6. **Tenant-safe by default:** workspace scope is present at every persistence and API boundary.

## Success criteria

Before expanding scope, a small pilot should demonstrate that users can find a party, understand the last meaningful interaction, see its connected commercial work, and identify the next owner/action without consulting another system.

## Implementation sequence and gaps

1. Wire authentication and workspace membership to request context.
2. Apply the initial PostgreSQL migration and build repository modules for parties, activities, work items, opportunities, and agreements.
3. Implement the documented API endpoints with validation, pagination, filtering, and audit fields.
4. Build the responsive web workspace: party search/list, 360-degree party view, timeline composer, work queue, and opportunity board.
5. Add authorization tests, tenant-isolation tests, migration tests, observability, backups, and deployment automation.
6. Pilot with realistic data, refine the controlled vocabularies, then prioritize integrations and analytics.

The repository currently includes only the schema, domain contracts, and health/meta API bootstrap. It does not yet implement authentication, persistence, CRUD endpoints, UI, search, audit history, or integrations.
